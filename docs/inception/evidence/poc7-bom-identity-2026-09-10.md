# POC-7 — telling the BOM types apart, and navigating one with no graph

Measured 2026-09-10 over 24 real BOMs. Re-run the classifier with
[`poc7-bom-type-discriminator.py`](poc7-bom-type-discriminator.py); it emits **shape only**, so its
output is safe to paste.

Fills two gaps a review found: ADR-0004 says an OBOM has no graph and that `ls` navigates it by
category, but neither the *discrimination rule* nor the *category vocabulary* was written down
anywhere except incidentally, as fixture values in `testdata/generate.py`.

## The rule: two spec-defined signals, not content sniffing

`lsxbom` must decide whether `tree` is meaningful **before** rendering anything. Guessing from
content is fragile; CycloneDX already carries the answer.

| Verdict | `metadata.lifecycles[].phase` | `metadata.component.type` | n |
|---|---|---|---|
| **OBOM** | `pre-build`, `operations` | `operating-system` | 14 |
| **image SBOM** | `pre-build`, `post-build` | `container` | 5 |
| **HBOM** | `operations` | `device` | 4 |
| **SBOM, undeclared root** | *(custom form — see below)* | **absent** | 1 |

`lifecycles` alone does not separate OBOM from HBOM; the root component type does. Together they
were unambiguous across every file measured.

## ⚠ The custom lifecycle form is real and easy to miss

A lifecycle entry is **either** `{"phase": "operations"}` — the enum — **or**
`{"name": ..., "description": ...}`, a free-text form. **Reading only `.phase` returns null for the
custom form and silently misclassifies the BOM.**

Found by re-measuring rather than by reasoning: the first version of this check reported the
outlier as having no lifecycle at all. It has one, and it says:

> `{"name": "Deployed", "description": "Inventoried from Ansible content installed on the
> controller filesystem (CISA SBOM type). Not Runtime: no playbook execution was observed, so
> this is what is installed and not what loaded."}`

That is a deliberate, well-formed use of the custom form to record which of the **six CISA SBOM
types** the document is — the distinction the `software-supply-chain-landscape` sibling records as
*independent* of what is inventoried.

### Provenance of that sample, stated because n=1

It was generated by **`ansible-bom`**, the sibling project, from an Ansible controller, and
**ansible-bom is still under development and may have bugs** — so this single file is not evidence
of general practice, and its shape may change. What survives regardless is the *spec* fact: the
custom form exists, is legal, and a `.phase`-only reader mishandles it.

⚠ It carries **no `metadata.component` at all**. That is schema-valid — `metadata` has no
`required` list, so the field is optional, and the document validates cleanly against
`bom-1.6.schema.json`. But a BOM with no root component never says *what it is about*, which is a
real problem for a consumer and the reason the classifier needs an "undeclared" branch.
**Worth raising with ansible-bom as a question, not asserted here as a defect.**

## Navigating an OBOM: the category vocabulary

An OBOM has no dependency graph (POC-2), so `ls` groups by the `cdx:osquery:category` property that
nearly every component carries. **40 distinct categories** across 14 OBOMs, and they partition by
platform rather than forming one list:

| Spread | Count | Reading |
|---|---|---|
| in **14 of 14** files | **6** | universal — present whatever the OS |
| in 9 of 14 | 16 | one platform group (9 hosts) |
| in 5 of 14 | 9 | the other platform group (5 hosts) |
| in 3–10 of 14 | 9 | partial rollout, or host-specific tooling |

The six universal ones: `users_snapshot`, `startup_items`, `shell_history_snapshot`,
`listening_ports`, `interface_addresses`, `certificates`.

**Consequence for `ls`**: the category list must be **discovered per document**, never hardcoded.
A fixed vocabulary would be wrong on most hosts, and wrong in a way that silently hides categories
rather than erroring.

**Consequence for `ls -l`**: there can be no fixed column set. Meaningful columns depend on the
category — a certificate wants issuer and expiry, a launchd service wants label and arguments.

## ⚠ Documented, NOT measured: the merged host view

cdxgen's `hbom --include-runtime` emits a combined HBOM+OBOM document which, per its documentation,
adds:

- deterministic **synthetic `bom-ref`s** for HBOM components that lacked them
- **host → hardware** dependency edges from `metadata.component`
- **hardware → runtime** edges, on *exact* evidence only — interface-name equality, driver /
  `kernel_modules` equality, device node / volume UUID / mount path, Secure Boot certificate
  identifiers. It explicitly refuses fuzzy name matching.

**This was read in cdxgen's docs and never run**, so no number here is measured. It matters because
it is the one shape in the OBOM/HBOM family where a host-level `tree` would be genuinely
meaningful — which would qualify ADR-0004's "an OBOM has no graph". The corpus holds HBOM and OBOM
as separate files, so the merged form has not been seen here.

**Open**: generate one and measure it. Until then, treat `tree`-on-a-host-view as unvalidated.

## What this changes

- The classifier is directly implementable and belongs in the tool, not in prose.
- The category vocabulary must be discovered, never hardcoded.
- ADR-0004's OBOM finding stands for plain OBOMs and carries an **unmeasured exception** for the
  merged host view.
